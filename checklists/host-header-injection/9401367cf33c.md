## Use case

The application improperly trusts the Host header, allowing an attacker to manipulate routing and potentially exploit various vulnerabilities such as password reset poisoning and SSRF.

## Steps to test

1. Set the Host header to a malicious domain (e.g., Host: evil.com).
2. Send a request to the target application and observe the response.
3. Test with variations of the Host header such as X-Forwarded-Host, X-Host, X-Forwarded-Server, and X-Original-Host.
4. Check for any unexpected behavior or responses that indicate trust in the manipulated Host header.

## Commands

```text
GET / HTTP/1.1
Host: evil.com
GET / HTTP/1.1
X-Forwarded-Host: evil.com
GET / HTTP/1.1
X-Host: evil.com
GET / HTTP/1.1
X-Forwarded-Server: evil.com
GET / HTTP/1.1
X-Original-Host: evil.com
Host: evil.com
X-Forwarded-Host: evil.com
X-Host: evil.com
X-Forwarded-Server: evil.com
X-Original-Host: evil.com
```
